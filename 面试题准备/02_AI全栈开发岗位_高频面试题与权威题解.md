## 一、全栈八股与核心通信协议

### Q1: 深度对比 SSE (Server-Sent Events) 与 WebSocket 在 AI 对话流式传输中的优劣，如何实现客户端主动中断与断网重连？

#### 【考点分析】
全栈岗对网络层与全双工/单工协议的考察，重点看工程落地的复杂度与边缘链路（如代理服务器、CDN、移动端切后台）的适配能力。

#### 【标准答案】
1. **核心技术选型对比**：

| 特性 | SSE (Server-Sent Events) | WebSocket |
| :--- | :--- | :--- |
| **通信模型** | 单向流（Server $\to$ Client），基于标准 HTTP/1.1 或 HTTP/2 | 全双工（Bidirectional），独立协议（ws:// 或 wss://） |
| **防火墙/网关兼容性** | 极佳，走标准 HTTP 端口（80/443），天然穿透反向代理与网关 | 较差，需要网关显式配置 `Upgrade: websocket` 支持 |
| **内置重连机制** | 规范原生支持 `Last-Event-ID`，浏览器断线自动重连并带上 ID | 需应用层自行实现心跳保活（Heartbeat ping/pong）与重连逻辑 |
| **协议开销** | 文本协议，轻量，基于 HTTP 报文 | 二进制/文本混合，握手协议较重，保持长连接消耗套接字资源 |
| **音频/实时多模态** | 较难支持低延迟双向语音（如 Gemini Live） | **最佳方案**，适合高频语音双向推流与手写画板同步 |

- **选型结论**：纯文本/富文本生成型对话，**优先选用 SSE**（简单、可靠、对 HTTP/2 多路复用友好）；包含实时语音交互、实时多人白板协作，**选用 WebSocket**。

2. **客户端主动中断（Stop Generating）的工程实现**：
   - **前端利用 `AbortController` 机制**：
     ```javascript
     const controller = new AbortController();
     // 点击“停止生成”按钮时执行
     stopButton.onclick = () => controller.abort();

     fetch('/api/chat/stream', {
       method: 'POST',
       body: JSON.stringify({ message: 'Hello' }),
       signal: controller.signal // 绑定 abort 信号
     }).catch((err) => {
       if (err.name === 'AbortError') console.log('用户主动取消');
     });
     ```
   - **后端资源联动释放（防止模型后台空跑扣费）**：
     FastAPI / Node.js 必须监听请求流断开事件。
     - FastAPI: 检测 `await request.is_disconnected()`，一旦客户端断开，立即调用 upstream LLM SDK 的取消信号或抛出 `asyncio.CancelledError`，及时终止上游 API 消费。

3. **断网重连与状态同步（State Resumption）**：
   - 后端在 SSE 事件流中为每个数据 Chunk 标注递增的序号或消息 ID（如 `id: msg_1024`）。
   - 客户端断网后重发请求，携带 `Last-Event-ID: msg_1024`，后端从 Redis 环形缓冲区中提取其断网期间错过的增量 Token 补发，保障内容连续不丢失。

### Q2: 前端在流式（Streaming）接收 Markdown 时，如何解决未闭合代码块、LaTeX 公式、Mermaid 图表的增量解析与渲染闪烁问题？

#### 【考点分析】
这是当前 AI 对话类应用（ChatGPT, Claude, Cursor 等）前端最具挑战性的用户体验细节，考验对 Markdown AST 抽象语法树与流式缓冲区的控制能力。

#### 【标准答案】
1. **未闭合代码块与语法标签闪烁问题**：
   - **现象**：当大模型输出 ` ```python\ndef add(a, b): ` 尚未输出末尾的 ` ``` ` 时，普通的 Markdown 解析器（如 marked, markdown-it）可能将其误判为普通文本，等结尾 ` ``` ` 到来瞬间突然“跳变”为代码高亮块，引发剧烈布局抖动与闪烁。
   - **解决方案**：
     - **预处理启发式闭合（Heuristic Auto-Closure）**：
       在将流式缓冲文本送入 Markdown 解析器前，通过轻量级正则检测未配对的反引号（` ``` `）数量。若为奇数，在文本末尾临时补全一个换行和 `\n``` ` 供解析器渲染，使中间态稳定显示为代码块容器。
     - **增量 AST 状态保留（Incremental Parsing）**：使用基于 AST 的流式渲染库（如 `stream-markdown` 或结合 `prosemirror`），将已解析的稳定 Node 缓存，仅对最末尾的叶子节点进行 Diff 更新。

2. **LaTeX 数学公式增量渲染（KaTeX / MathJax）**：
   - 当 `$$` 或 `\(` 尚未成对出现时，避免调用昂贵的 KaTeX 编译。通过状态扫描器判断公式是否闭合，未闭合时维持纯文本占位符，闭合后再调用 KaTeX 生成 MathML / HTML。

3. **Mermaid 图表与重型可视化组件延迟渲染**：
   - Mermaid 生成图表需要完整合法的图表定义语法（如 `graph TD; A-->B`），中间不完整的流式文本会导致 Mermaid 编译器报错抛出 Red Error Box。
   - **策略**：在流式输出阶段，仅将其渲染为普通的代码块（带加载动画指示器）；只有当识别到该代码块的 ` ``` ` 闭合标记，且会话处于 `done` 状态（或停止流式传输）后，再触发一次微任务调用 `mermaid.render()` 渲染 SVG。

### Q3: 详述现代工业级 RAG 完整流程：从分块策略、混合检索（BM25 + Dense Vector）到重排（Rerank）的最佳实践

#### 【考点分析】
RAG 是 AI 全栈岗位最核心的考核模块。面试官关注应聘者是否脱离了最幼稚的“文本定长切片 + 暴力向量检索”，具备解决工业界复杂文档问答的能力。

#### 【标准架构流程图】

```
原始文档 (PDF/Markdown/Word)
       │
       ▼
【智能分块 (Semantic Chunking / Parent-Child)】
       │
       ├──────────────────────────────┐
       ▼                              ▼
【稠密向量写入 (Dense Index)】  【稀疏倒排索引写入 (BM25 / Sparse)】
       │                              │
═══════╪══════════════════════════════╪═══════════════════════════
       ▼ 查询阶段                     ▼ 查询阶段
用户 Query  ─────────────────► 双路检索 (Hybrid Retrieval)
                                      │
                                      ▼
                        【倒数融合排名 (RRF) 粗排 Top-50】
                                      │
                                      ▼
                        【交叉编码重排 (Cross-Encoder Rerank) Top-5】
                                      │
                                      ▼
                        【上下文压缩与 Prompt 注入】
                                      │
                                      ▼
                               LLM 生成回答 (带引用角标)
```

#### 【关键技术细节解析】
1. **分块策略（Chunking Strategies）**：
   - **固定字符切分（Fixed-size with overlap）**：易截断句子与语义，只适合演示。
   - **语义分块（Semantic Chunking）**：计算连续句子之间的 Embedding 相似度，当相似度突变超过阈值时进行切分，保证单个 Chunk 内部语义高度内聚。
   - **父子文档切分（Parent-Child / Hierarchical Chunking）**：将文档切分为较大的 Parent Chunks（如 1000 tokens，保持完整上下文），并进一步切成细粒度 Child Chunks（如 150 tokens，用于精准向量检索）。检索命中 Child 时，实际将对应的 Parent 送给 LLM，既解决检索匹配精度，又解决回答缺乏宏观背景的问题。

2. **混合检索（Hybrid Search: Dense + Sparse）**：
   - **Dense (稠密向量，如 text-embedding-3, BGE)**：擅长同义词、意图理解与跨语言匹配，但对专有名词、产品型号、错误码（如 `ERR_CONN_RESET_4001`）极度不敏感。
   - **Sparse (稀疏检索，如 BM25, SPLADE)**：基于词频与逆文档词频，对专有名词、精确编号检索命中率极高。
   - **融合算法（RRF - Reciprocal Rank Fusion）**：
     $$RRF\_Score(d) = \sum_{m \in \{Dense, Sparse\}} \frac{1}{k + rank_m(d)}$$
     无需归一化不同算法的绝对相似度分数，通过排名位置相加，鲁棒性极佳。

3. **重排层（Reranker）**：
   - 使用 Cross-Encoder 模型（如 `bge-reranker-large`, `cohere-rerank`），将 `(Query, Document)` 作为一个完整对输入模型进行全注意力交互。
   - 相比 Bi-Encoder（向量检索），Cross-Encoder 计算延迟高（每对需几十毫秒），因此只用于对混合检索粗排出的 Top 20~50 进行精细打分，过滤掉伪相关文档，最终挑选 Top 3~5 传给大模型。

### Q4: 向量数据库核心索引算法（HNSW vs IVF-FLAT）原理是什么？PGVector、Qdrant、Milvus 如何根据业务场景选型？

#### 【考点分析】
考核应聘者对底层向量相似度计算数学原理及实际工程落地的基础设施选型权衡能力。

#### 【标准答案】
1. **核心索引算法对比**：
   - **IVF-FLAT (Inverted File Flat - 倒排文件索引)**：
     - **原理**：利用 K-Means 聚类将向量空间划分为 $K$ 个簇心。查询时先计算与 $K$ 个簇心的距离，只在距离最近的几个簇内进行暴力比对。
     - **优劣**：内存占用较小，建索引速度快；但召回率（Recall）受限于聚类质量与 $nprobe$ 参数，存在边界误判。
   - **HNSW (Hierarchical Navigable Small World - 分层可导航小世界图)**：
     - **原理**：多层跳表（Skip-list）结构的图网络。顶层稀疏图实现快速长距离“跳跃”，底层密集图进行局部精细搜索（贪婪向前遍历最近邻居）。
     - **优劣**：工业界**事实上的标准**。检索速度极快（微秒级对数复杂度），召回率极高（通常 >98%）；缺点是内存开销大（除了向量数据本身还要存储图拓扑指针），索引构建时间长。

2. **主流向量数据库选型矩阵**：

| 产品 | 底层架构 / 语言 | 优势 | 劣势 | 推荐适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **PGVector** | PostgreSQL 插件 (C) | 零额外运维成本；支持与业务关系型数据（用户、订单、权限表）在**同一个事务中 ACID 联表查询** | 数据量过数百万后内存消耗大，QPS 吞吐上限低于专用向量库 | **中小规模（< 500 万向量）、已有 PG 技术栈的企业应用**（性价比最高） |
| **Qdrant** | 独立向量库 (Rust) | 单机性能极佳，内存管理精细；**Payload Filter（元数据过滤）极强**，支持硬件量化（Scalar/Product Quantization）压缩 4x 内存 | 分布式集群模式相比 Milvus 略显年轻 | **中大规模（千万级）、重度依赖复杂业务属性过滤与独立微服务架构** |
| **Milvus** | 分布式系统 (Go + C++) | 真正的云原生分布式架构，计算与存储分离（支持 S3 存储），支持亿级至百亿级海量向量水平扩展 | 架构极其庞大繁琐（依赖 etcd, MinIO, Pulsar/Kafka），运维门槛极高 | **超大规模、海量多租户 SaaS、顶级大厂数据中台** |

### Q5: 解释语义缓存（Semantic Cache / GPTCache）与 Prompt Caching 的区别，如何在架构中协同落地？

#### 【考点分析】
考察全栈工程师在 LLM 系统架构中降本增效的核心抓手，区分应用层缓存与服务商前缀缓存的不同层级。

#### 【标准答案】
1. **语义缓存（Semantic Cache - 应用层）**：
   - **工作原理**：当用户提问时，系统将 Query 转化为向量，在向量缓存库（如 Redis Vector Search）中检索历史相似 Query。如果两者的 Cosine 相似度高于预设阈值（如 > 0.96），则判定为“语义同义”，直接返回上次缓存的答案，**完全无需请求上游大模型**。
   - **优点**：节省 100% 的上游 API 费用，延迟从几秒直降至 10ms 级别。
   - **缺点**：对于时效性敏感或个性化强的提问容易造成“答非所问”。

2. **Prompt Caching（前缀上下文缓存 - 模型推理层）**：
   - **工作原理**：主流大模型服务商（Anthropic, Gemini, OpenAI, DeepSeek）在服务端 GPU 显存中保留了重复输入前缀的 **KV Cache**。只要本次请求的前部上下文与之前某次请求的前缀完全吻合，该部分无需重复计算 Attention。
   - **优点**：准确率 100%（不改变模型的生成逻辑），成本立减 50%~90%，TTFT 降低数倍。

3. **双层协同架构落地最佳实践**：
   ```
   用户提问 ──► [Layer 1: 语义缓存 (GPTCache/Redis)] 
                     │ 命中 (相似度 > 0.95)? ──► 立即返回历史回答 (0 Token 消耗, <20ms)
                     │ 未命中
                     ▼
                 [Layer 2: 组装 Prompt]
                     ├─ 头部: 静态 System Prompt + 基础规则 (命中模型提供商 Prompt Cache)
                     ├─ 中部: 固定的工具定义 Schema (命中 Prompt Cache)
                     └─ 尾部: 动态变量 (用户 Query + 本次召回的知识切片)
                     ▼
                 [调用上游 LLM] ──► 异步写入 Layer 1 语义缓存备用
   ```

### Q6: FastAPI + AsyncIO 与 Next.js App Router 在构建大模型应用后端的职责边界与并发性能模型对比

#### 【考点分析】
考察应聘者是否能够科学地划分前后端技术栈架构，避免将重型 AI 编排逻辑不合理地堆砌在 Next.js Server Actions 或前端无服务器云函数中。

#### 【标准答案】
1. **职责边界最佳划分**：
   - **Next.js (BFF 层 / 前端与用户交互)**：
     - 负责 SSR/SSG 页面渲染、用户认证（NextAuth/Clerk）、会话路由、客户端 SSE 事件消费、Markdown 动态流式组件渲染。
     - 适合做轻量的 Gateway 转发或直连简单会话接口。
   - **FastAPI / Python (AI Core 引擎层)**：
     - 负责复杂的 RAG 检索管线（LangChain/LlamaIndex）、向量库操作、调用 Python 原生生态（NumPy, PyTorch, Pandas）、本地轻量模型（Reranker/Whisper）托管、多智能体图引擎（LangGraph）。

2. **并发模型与生产陷阱**：
   - **FastAPI 中的同步阻塞陷阱**：
     - 许多初学者在 FastAPI 中使用 `async def chat(...)`，但在内部直接调用了同步阻塞的库函数（如 `requests.post()`、同步向量检索或未异步化的 DB 查询）。这会导致**主线程 Event Loop 被硬生生阻塞**，即使部署了 4 个 Worker，也会在几十个并发下彻底挂起。
     - **规范**：I/O 操作必须使用原生异步库（`httpx.AsyncClient`, `asyncpg`, `aiofiles`）；若必须调用同步 CPU 密集型任务，必须包裹在 `await run_in_threadpool(...)` 或 `asyncio.to_thread()` 中。
   - **Next.js Edge / Serverless 的超时限制**：
     - Vercel 等 Serverless 平台有 10s~60s 的执行超时限制（Execution Timeout）。对于耗时很长的 Agent 自主推理或复杂 RAG 生成，直连 Serverless 极易遭遇 `504 Gateway Timeout`。长耗时流必须交由独立长连接服务（如常驻 ECS/K8s 上的 FastAPI 容器）支撑。

### Q7: 【场景设计】设计一个支持百万级文档、多租户行级权限隔离、溯源高亮引用的企业级知识库问答（RAG）系统

#### 【核心架构设计】

```
   [前端应用 (React/Next.js)] 
         │ (SSE 流式连接，解析并高亮 Citation 角标 [1], [2])
         ▼
   [API 网关 / BFF (鉴权 & 租户上下文解析: tenant_id, user_role)]
         │
         ▼
   [RAG 编排引擎 (FastAPI / Hybrid Retrieval)]
         │
         ├─ 1. 过滤查询 (Payload Filter: tenant_id == 'T1' AND group_id IN ('admin', 'dev'))
         ├─ 2. 向量库检索 (Qdrant / PGVector with Row-Level Security)
         ├─ 3. 获取 Top-K 文档切片及原始元数据 (doc_id, page_number, bounding_box, text)
         ▼
   [LLM 组装与生成]
         │ (Prompt 强制要求每个结论必须附加 [doc_id:page] 引用标记)
         ▼
   [流式输出给前端]
         │ 客户端点击 [1] ──► 弹窗唤起 PDF.js ──► 精确跳转并高亮 page_number 区域
```

1. **多租户安全与行级权限隔离（Tenant & Row-Level Security）**：
   - **方案 A（向量库元数据过滤）**：每个 Chunk 插入向量库时，附加 Payload：`{ tenant_id: "corp_A", allowed_roles: ["finance", "executive"], doc_id: "doc_123" }`。在检索向量前，**强制执行 Pre-filtering（预过滤）**，未授权的文档物理级不可见。
   - **方案 B（PGVector + Postgres RLS）**：利用 Postgres 原生的 `CREATE POLICY`，基于 `current_setting('app.current_user_id')` 自动生效行级过滤，杜绝应用层写错 SQL 导致越权泄密。

2. **精准溯源与高亮引用（Citation & Grounding）的工程闭环**：
   - **切块阶段**：切片时不能只存纯文本，必须把切片在源文件中的坐标打在元数据上（如 PDF 的 `page: 5, bbox: [x0, y0, x1, y1]`）。
   - **模型约束**：通过 System Prompt 约定：“回答时每一句核心陈述必须附加切片 ID，例如：`公司 2023 年营收增长 15% [ref:chunk_992]`”。
   - **前端交互闭环**：前端自定义 Markdown 解析器识别 `[ref:chunk_992]`，渲染为可点击的小角标。点击角标后，右侧双栏联动展开 PDF 预览器（基于 PDF.js），自动滚动到第 5 页，并在指定坐标绘制半透明高亮矩形框。

### Q8: 【场景设计】设计一个高可用生产级 LLM API 网关：支持多厂商负载均衡、故障自动容灾转移、Token 速率配额与成本审计

#### 【架构方案要点】
1. **多厂商统一适配与负载均衡（Multi-Provider Fallback）**：
   - 统一抽象为兼容 OpenAI 协议的输入输出接口。
   - 配置故障转移策略树（Fallback Chain）：主路 `DeepSeek-V3` $\to$ 遇 5xx 故障自动瞬时切往 `GPT-4o-mini` $\to$ 再挂切往 `Claude-3.5-Haiku`。
   - 配置健康检查（Health Check）熔断器：某厂商在 30 秒内连续出现 5 次错误，主动打开熔断器（Open State），降级绕行 1 分钟后进入半开试探（Half-Open）。

2. **Token 级精细流控与限流（Rate Limiting）**：
   - 传统的 HTTP 请求限流（如 Nginx 限每秒 10 个请求）无法防范 LLM 场景（一个请求可能输入 100k Token，瞬间耗尽并发配额）。
   - **双轨令牌桶算法（Token Bucket by RPM & TPM）**：
     - **RPM (Requests Per Minute)**：防范刷接口 DDOS。
     - **TPM (Tokens Per Minute)**：在请求到达时，先用 `tiktoken` 估算输入 Token，从 Redis TPM 令牌桶中预扣除；请求流式结束后，根据实际返回的 Token 数做多退少补校准。

3. **企业级租户计费与审计日志（Audit & Ledger）**：
   - 利用异步消息队列（Kafka / RabbitMQ）解耦计费与审计，避免将日志入库操作放入热点请求路径中。
   - 记录字段：`request_id`、`tenant_id`、`model`、`prompt_tokens`、`completion_tokens`、`cached_tokens`、`duration_ms`、`cost_usd`。

### Q11: 【前端性能】长对话富文本流式输出下的 DOM 节点暴增与内存泄漏治理（页面掉帧卡顿如何解决？）

#### 【故障现象】
连续对话几十轮后，单页内存在大量 Markdown 格式文本、几十个代码高亮框、SVG 图表。页面滚动极其卡顿，甚至浏览器标签页崩溃（OOM）。

#### 【工业级优化方案】
1. **长列表虚拟化渲染（Virtual List）**：
   - 使用 `@tanstack/react-virtual` 或 `virtuoso`。
   - 只渲染当前视口（Viewport）可见的 5~8 条对话卡片，视口外的内容用绝对定位的空白占位 DIV 替代，使整个页面的 DOM 节点数始终控制在几百个以内。
2. **动态自适应视口跟踪（Pin to Bottom）**：
   - 流式输出时，页面需自动跟随最新 Token 滚动到底部。如果无脑在每个 Chunk 触发 `window.scrollTo()`，会引发高频重排（Reflow/Layout Thrashing）。
   - **优化**：使用 `requestAnimationFrame` 防抖合并滚动事件；监听用户主动向上滚动的动作，一旦用户向上翻看历史，立即解除锁定，暂停自动滚底。
3. **代码高亮与重型组件惰性加载（Lazy Initialization）**：
   - 避免在流式接收阶段对代码块执行 Prism.js / Highlight.js 的逐字正则全量高亮重绘。
   - 采用纯 CSS 实现基础等宽字体，等流式状态标记为 `complete` 后，利用 `requestIdleCallback` 调度代码语法高亮分块计算。

### Q12: 【线上故障】高并发突发流量下，上游模型接口频繁返回 429 (Rate Limit) 或向量库连接池耗尽导致级联雪崩，如何排查与治理？

#### 【线上事故演练与治理】
1. **排查流程**：
   - 查看 APM（如 Sentry / Prometheus）监控仪表盘，观察错误状态码分布。
   - 区分 429 的具体来源：是企业账号的总并发超限、TPM 超限，还是上游模型厂商集群不可用？
   - 检查向量数据库活跃连接数（Active Connections），观察是否因为长耗时未释放连接导致连接池耗尽。

2. **三道防线治理架构**：
   - **第一道防线：指数退避重试（Exponential Backoff with Full Jitter）**：
     捕获 429 异常，读取响应头中的 `Retry-After`。若无，采用全抖动指数退避：
     $$T_{wait} = \text{random}(0, \min(T_{max}, T_{base} \times 2^{retry}))$$
     避免成百上千个重试请求在同一精确毫秒同时击穿上游。
   - **第二道防线：异步任务缓冲池与自适应漏桶（Adaptive Queueing）**：
     当并发量达到上游承受极限时，将实时 Web 请求转为异步 Job，推入 Redis / Celery 任务队列中按配额匀速消费，并给用户返回排队进度（“当前排队第 3 位，预计 5 秒内开始回答”），化解同步超时雪崩。
   - **第三道防线：向量库连接池与异步会话治理**：
     - 禁止在每个请求中新建向量库 Client。在 FastAPI 生命周期 `lifespan` 中单例初始化全局异步连接池。
     - 严格设置连接池上限（`max_size=50`, `timeout=5.0`），配置断开回收机制，防止长事务僵死连接霸占池资源。
