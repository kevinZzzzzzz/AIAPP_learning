# 术语速查表

> 用途：遇到不认识的词随时查。**按"人话解释 + 为什么重要"的方式写**，
> 不堆定义。面试时能用一句话解释清楚一个术语，比背术语表更有价值。

---

## 一、基础概念

| 术语 | 英文 | 一句话解释 | 为什么重要 |
|---|---|---|---|
| 大语言模型 | LLM | 用海量文本训练出来的、能预测下一个词的模型 | 一切的基础 |
| Token | Token | 模型处理文本的最小单位，不是字也不是词 | 计费和上下文限制都按它算 |
| 上下文窗口 | Context Window | 模型一次能处理的最大 token 数 | 决定了你能塞多少资料，RAG 的起因 |
| 自回归 | Autoregressive | 模型逐字生成，每个字都基于前面已生成的内容 | 这就是流式输出能实现的原因 |
| 温度 | Temperature | 控制输出的随机性。低=稳定，高=多样 | 工具调用/RAG 要用低温 |
| Top-p / Top-k | Nucleus / Top-k Sampling | 采样范围的限制方式，和温度类似作用 | 一般只调一个，别同时调 |
| 幻觉 | Hallucination | 模型自信地说出错误内容 | RAG 不能消除它，只能缓解 |
| 思维链 | CoT (Chain of Thought) | 让模型显式写出推理步骤，效果更好 | 复杂推理的必备技巧 |

## 二、RAG 相关

| 术语 | 英文 | 一句话解释 | 为什么重要 |
|---|---|---|---|
| 检索增强生成 | RAG | 先检索相关资料，再让模型基于资料回答 | 解决模型不知道你私有数据的问题 |
| 向量 | Vector / Embedding | 把文本变成一串数字，语义相近则数字也相近 | 让"意思相近"可以被计算 |
| 向量维度 | Dimension | 这个向量有多少个数字（如 1024 维） | 维度和模型绑定，混用会出错 |
| 余弦相似度 | Cosine Similarity | 看两个向量的夹角，判断语义接近程度 | 最常用的相似度度量 |
| 归一化 | Normalization | 把向量长度缩放到 1 | 归一化后余弦相似度=点积，算得更快 |
| 切片 | Chunking | 把长文档切成小段 | **最影响 RAG 效果的一步** |
| 重叠 | Overlap | 相邻片段之间重复一部分内容 | 防止答案正好卡在边界被切断 |
| 召回 | Recall | 从库里找出可能相关的片段 | 召回质量决定 RAG 上限 |
| Top-K | Top-K | 取相似度最高的 K 个结果 | 调大噪声多，调小会漏 |
| BM25 | BM25 | 经典的关键词检索算法 | 精确匹配的强项，与向量互补 |
| 混合检索 | Hybrid Search | 向量 + 关键词两路一起用 | 单一方案都会在某类查询上瘸腿 |
| RRF | Reciprocal Rank Fusion | 用"排名"而非"分数"融合多路结果 | 避免量纲不同的问题，实现简单 |
| 重排 | Rerank | 粗召回后用小模型精排 | 显著提升 Top-K 准确率 |
| Cross-encoder | Cross-encoder | 同时看 query 和文档打分（更准但更慢） | 这是 rerank 比向量检索准的原因 |
| 相似度检索 | ANN | 近似最近邻，用少量精度换大量速度 | 大规模检索的必需技术 |
| 忠实度 | Faithfulness | 答案是否完全基于检索到的资料 | RAG 评估的核心指标 |
| 查询改写 | Query Rewriting | 把模糊问题改写成多个清晰的检索式 | 提升模糊问题的召回率 |
| HyDE | HyDE | 让模型先"假装回答"，用生成的答案去检索 | 因为答案和文档的语义更接近 |

## 三、Agent 相关

| 术语 | 英文 | 一句话解释 | 为什么重要 |
|---|---|---|---|
| 智能体 | Agent | 能自主决策、调用工具、多步完成任务的程序 | 让 AI 从"会说"变成"会做" |
| 工具调用 | Tool Calling / Function Calling | 模型输出"我想调某函数"的 JSON，由你的代码执行 | Agent 的核心机制 |
| ReAct | ReAct | 思考 → 行动 → 观察 的循环模式 | 所有 Agent 框架的骨架 |
| 观察 | Observation | 工具执行后返回给模型的结果 | 模型据此决定下一步 |
| 系统提示 | System Prompt | 设定模型角色和规则的最优先指令 | 决定 Agent 的行为基调 |
| 步数上限 | max_steps | 最多循环几次，防止死循环 | **必须有的硬刹车** |
| 人在环 | Human-in-the-Loop | 危险操作前暂停，等人确认 | 安全底线 |
| 提示注入 | Prompt Injection | 把恶意指令藏在模型会读到的内容里 | 最重要的安全风险 |
| 沙箱 | Sandbox | 限制程序只能操作特定目录 | 防止越权访问文件 |
| 最小权限 | Least Privilege | 只给完成任务所需的最小工具集 | 减少 Agent 能造成的破坏 |
| 多智能体 | Multi-Agent | 多个 Agent 分工协作 | 不是所有场景都需要，可能反而更糟 |
| 主管模式 | Supervisor | 一个协调 Agent 分派任务给专家 Agent | 最常见的多 Agent 架构 |
| 工作流 | Workflow | 流程写死，不做自主决策 | **能用它就别用 Agent** |
| 上下文管理 | Context Management | 控制发给模型的对话历史长度 | 直接决定成本和可行性 |
| 摘要压缩 | Summarization | 把老对话压成摘要，保留要点 | 缓解历史带来的成本膨胀 |

## 四、工程与部署

| 术语 | 英文 | 一句话解释 | 为什么重要 |
|---|---|---|---|
| SSE | Server-Sent Events | 服务器单向持续推送事件的 HTTP 技术 | LLM 流式输出的首选方案 |
| WebSocket | WebSocket | 全双工通信协议 | 需要客户端高频上行时才用 |
| 首字延迟 | TTFT | 从请求到收到第一个字的时间 | 流式输出主要改善这个指标 |
| 事件协议 | Event Protocol | 定义推给前端的事件类型和格式 | 前后端解耦的关键 |
| CORS | Cross-Origin Resource Sharing | 浏览器跨域限制，前后端分离必须配 | 本地好好的上线就报错的原因 |
| 代理缓冲 | proxy_buffering | Nginx 默认会攒着响应再发 | 会让流式效果失效的坑 |
| 异步 | Async / Await | 不阻塞地等待 IO | LLM 应用必须用异步 |
| 事件循环 | Event Loop | 异步任务调度的机制 | 同步调用会阻塞它，导致全站卡 |
| 限流 | Rate Limiting | 限制请求频率 | 防滥用，保护成本 |
| 可观测性 | Observability | 能看清系统内部发生了什么 | 线上排查的前提 |
| 追踪 | Tracing | 记录一次请求的完整链路 | 定位问题在哪一环 |
| 评估集 | Eval Set | 人工标注的"问题→正确答案"集合 | **没有它，调参都是玄学** |
| 命中率 | Hit Rate | 正确答案出现在召回结果里的比例 | 衡量检索质量 |
| MRR | Mean Reciprocal Rank | 正确答案排名的倒数的平均值 | 衡量排序质量 |

## 五、模型与生态

| 术语 | 英文 | 一句话解释 | 为什么重要 |
|---|---|---|---|
| 微调 | Fine-tuning | 用你的数据继续训练模型 | 解决"怎么说"（风格），不解决"说什么" |
| 蒸馏 | Distillation | 用大模型的输出训练小模型 | 降本提速 |
| 量化 | Quantization | 用更少的位数存模型权重 | 让大模型能在消费级硬件上跑 |
| 上下文缓存 | Prompt Caching | 缓存重复的 prompt 前缀 | 生产环境省钱利器 |
| MCP | Model Context Protocol | Agent 连接外部工具/数据的标准协议 | 解耦工具与框架 |
| 结构化输出 | Structured Outputs | 用 Schema 约束模型输出格式 | 保证程序能可靠解析 |
| 约束解码 | Constrained Decoding | 在生成时限制只能输出符合格式的 token | 结构化输出的底层实现 |
| AI SDK | Vercel AI SDK | 前端 AI 交互的主流库 | 封装了流式/状态管理 |
| LangGraph | LangGraph | Agent 编排框架 | 提供持久化和人在环 |
| AgentOps | AgentOps | Agent 的运维体系（监控/评估/成本） | 从 demo 到产品的必经之路 |

## 六、容易混淆的几组概念

### RAG vs 微调

| | RAG | 微调 |
|---|---|---|
| 解决什么 | **说什么**（知识、事实） | **怎么说**（风格、格式） |
| 更新 | 改文档即时生效 | 要重新训练 |
| 成本 | 低（按次调用） | 高（训练+部署） |
| 幻觉 | 不能消除，但可溯源 | 不能消除 |
| 什么时候用 | 90% 的场景 | 需要固定输出风格/专业术语 |

### 向量检索 vs 关键词检索

| | 向量 | BM25 |
|---|---|---|
| 擅长 | 语义相近、口语化、同义改写 | 精确字符串、型号、错误码、人名 |
| 弱点 | 精确字符串会漏 | 同义改写会漏 |
| 结论 | **两个都要**（混合检索） | |

### Workflow vs Agent

| | Workflow | Agent |
|---|---|---|
| 流程 | 写死的 | 模型自主决定 |
| 可靠性 | 高 | 低（不确定性是代价） |
| 成本 | 可预测 | 不可预测 |
| 什么时候用 | 流程明确、要求稳定 | 任务开放、需要多步决策 |
| 建议 | **能用 Workflow 就别用 Agent** | |

### SSE vs WebSocket

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务器→客户端） | 全双工 |
| 协议 | 普通 HTTP | 需协议升级 |
| 重连 | 浏览器原生支持 | 要自己实现 |
| 适合 | **LLM 流式输出** | 语音对话、协同编辑 |

## 七、记住这张"核心链条"

如果只能记一件事，记这个 —— 它是整条技术脉络：

```
模型只能预测下一个词
   ↓
所以它会"幻觉"（不知道就说，答错也自信）
   ↓
所以要 RAG（给它真实资料，让它"照着说"）
   ↓
但资料太长放不下、太贵 → 所以要先"检索"
   ↓
检索要准 → 所以要"混合检索 + 重排"
   ↓
但模型只会"说"不会"做" → 所以要"工具调用"
   ↓
工具调用要循环、要记忆、要安全 → 所以有"Agent"
   ↓
Agent 要给真人用 → 所以要"后端服务 + SSE 流式 + 前端交互"
   ↓
上线要可靠、要省钱、要能发现问题 → 所以要"评估 + 监控 + 成本控制"
```

**看懂这条链条，你就理解了整个 AI 应用开发领域为什么是现在这个样子。**
